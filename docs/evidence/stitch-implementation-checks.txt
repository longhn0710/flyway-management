Backend/API mapping and safety boundaries
-----------------------------------------
The reviewed screen-to-API contract is in
`docs/design/oracle-console/api-mapping.md`; the implementation routes are in
`internal/httpapi/phase2.go`, `internal/httpapi/connections.go`, and
`internal/httpapi/execution.go`. Oracle currently uses the established target,
connection, registered-schema and execution-account APIs. PostgreSQL, MySQL,
and SQL Server have no engine discriminator, driver/runtime, discovery, or
execution API. They must remain disabled future options. Other unavailable
capabilities relevant to the Stitch pages are:

- No aggregate dashboard/metrics endpoint or collection total counts.
- No `/migration-runs/{id}/events` SSE route; status and searchable logs use
  polling APIs.
- No persisted last-connection-test timestamp or general live database catalog
  endpoint for regular schema users; the connection wizard returns transient
  Oracle discovery, then re-discovers during atomic save.
- No standalone endpoint for saving discovery results or for creating only a
  target in the connection wizard flow.

The existing server remains the authorization authority. Browser cookie
mutations require a matching Origin and CSRF token; roles and target/schema
grants scope operational access, including Admin execution and explicit PROD
authorization. Oracle credentials have write-only APIs and remain encrypted in
SQLite. The allowlist restricts application choices but grants no Oracle
privileges. Migration input is immutable; preflight precedes explicit
confirmation and idempotent asynchronous submission. Queued work rechecks
authorization and frozen configuration. Cancellation applies only while
queued; it does not roll back SQL. Run history/log/repair APIs expose recorded
evidence, with no generic retry or arbitrary SQL endpoint. These controls and
the existing SQLite migration history were left unchanged.
