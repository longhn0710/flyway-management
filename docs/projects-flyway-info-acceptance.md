# Projects and native Flyway Info — operator acceptance, 2026-10-16

Implemented locally for review. No source or GitOps push, deployment, infrastructure change, migration submission, repair, baseline, clean or SQL replay was performed against Oracle. The existing Go service, SQLite, credential store, pinned runtime and asynchronous migration pipeline remain the execution architecture.

## Operator behavior

Projects is now in primary navigation. An Admin can create a named project with an immutable generated identifier, description, status and timestamps; select schema references or whole-instance scopes; edit; archive; and restore. A shared instance can appear in several projects. A project may span environments, and registered schemas remain valid without any project assignment. Archived projects permit metadata edits and restoration, with membership changes requiring restoration first.

Project members are references to existing registry IDs. There are no copied connections, credentials, history rows or new project roles. Only Admins change organization, using the existing administrative permission and audited mutation path. Operators and Viewers see projects with readable resources and only authorized member references. A schema-only reader can navigate the authorized schemas of an instance membership without receiving hidden schema records. Inactive references remain visible to Admins for maintenance.

Project history means **runs for current member scopes intersected with current run read permissions**. Adding a member includes its prior runs; removing it removes those runs from this view. Instance scopes include current and future registered schemas. Overlapping instance/schema references do not duplicate runs. Filters and pagination apply to the combined ordered result. Original destination, requester, execution-account and runtime snapshots stay immutable; no historical project-at-execution attribution is invented or backfilled.

A project resource links to its instance, canonical schema page, native Info, permitted migration flow and schema history. The existing history view provides run destinations, artifact, requester/source, execution account, time and outcomes. Run Details retains Searchable Logs as the execution-log viewer.

## Native Flyway Info

A dedicated `/flyway-info` view is linked from schema details, project resources and Run Details. It presents Category, Version, Description, Type, Installed On, State and Undoable in a full-width native table. Search covers version, description and file paths; state/category filters, native-state counts, sorting and pagination support larger results. The details drawer retains all row metadata, including Installed By, Execution Time, filepath, raw version and additional CLI fields. Keyboard focus returns to the row on close.

Recorded mode reads the newest standalone capture or native `info` execution from a migration run. A run-specific link stays historical. The source run/execution, selected artifact/hash, effective file manifest and capture timestamp identify the evidence. Account, history location, endpoint, schema/runtime version and CLI-reported database identity are available in capture details. The interface always identifies recorded state as historical and warns if destination/history configuration drifted. Failed captures remain visible rather than falling back silently to older success or a false empty history.

Refresh requires the existing `operate` permission (including explicit PROD authorization), active target/schema/account, mapped account and schema allowlist, configured credential and a suitable immutable artifact. Operators can upload an immutable SQL/ZIP package or reuse the recorded artifact. The same plan builder reconstructs stored stream files, verifies checksums/configuration/runtime pin, rejects held or busy streams and dedicated unverified history configurations, and rechecks current authority before dispatch. The only dispatched command is the literal **`info`**. No migration job or stream reservation is created. Runtime integrity verification, private temporary TOML configuration, credential redaction, callback exclusion, resource/output limits and process cleanup are reused. The inspection budget is at most 45 seconds; HTTP grants a 50-second budget, with a short independent evidence-persistence budget after cancellation.

New captures are append-only SQLite evidence, separately audited and stored outside migration runs. Migration safety logic is unchanged. Unsafe native states remain visible with `HISTORY_UNSAFE` context; they never become migration authorization or bypass a stream hold. Historical execution identity follows the existing readable-run evidence policy; Viewers do not fetch the execution-account administration/catalog API.

A stored/normalized package cannot independently prove completeness against external migration sources. The UI therefore warns that Pending/Missing and related resolver states depend on captured files. Missing files, failed inspection and malformed/missing native tables have explicit diagnostic states. Original bounded/redacted stdout, stderr and JSON remain available under Detailed diagnostics, with a link to associated run logs where applicable.

## Delivery limits

SQLite migrations 005 and 006 add organizational and inspection tables. Migration 007 widens the existing environment constraint to include SIT, using a transactional table rebuild with a dedicated connection, foreign-key validation and enforcement restoration. Upgraded installations require schema version 7; the existing checksum ledger, startup verification and original encryption key requirements remain in force. There is no downgrade migration or automatic project backfill. Follow the established consistent SQLite/key backup procedure before any later authorized rollout; an older binary rejects this newer registry version. Nothing has been pushed or deployed.

The SIT upgrade follows SQLite’s [documented table-rebuild sequence](https://www.sqlite.org/lang_altertable.html#making_other_kinds_of_table_schema_changes), preserving child references and rejecting unexpected custom target indexes/triggers instead of silently dropping them. The native table and artifact-relative interpretation follow Redgate’s [Info command documentation](https://documentation.red-gate.com/flyway/reference/commands/info); callback exclusion uses the existing runtime policy, consistent with Redgate’s [callback cautions](https://documentation.red-gate.com/flyway/reference/callback-events).

Project lists and project history reuse existing authorized registry/run enumeration. This is appropriate for the current lightweight registry; large fleets may need measured backend aggregation work later. Existing engine/PROD/history safeguards remain in place. Complete external migration-source provenance is outside this phase, so artifact limitations remain explicit even after successful refresh.
