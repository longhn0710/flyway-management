## Execution and recovery contract

The original unbounded fixture was freshly reproduced with CLI PID/process group and PostgreSQL backend correlation. The JDBC session recorded statement/transaction/lock timeouts and `client_connection_check_interval` as zero. In this reproduction, CLI termination did not stop the running statement. PostgreSQL 17 [documents](https://www.postgresql.org/docs/17/runtime-config-connection.html#GUC-CLIENT-CONNECTION-CHECK-INTERVAL) that zero disables periodic connection checks and defers disconnect detection until socket activity. The evidence shows: SQL was active, the client exited 143, and the backend was still active after ten seconds. A later observation found the backend gone and no successful timeout history row. Neither observation proves a whole-run rollback. The original failure remains retained.

The PostgreSQL runtime now supplies fixed JDBC startup options on every execution connection. Statement, transaction, idle-session and idle-in-transaction limits equal the configured Manager execution budget; lock timeout is at most five seconds. PostgreSQL 17 [defines the transaction limit as session termination](https://www.postgresql.org/docs/17/runtime-config-client.html#GUC-TRANSACTION-TIMEOUT). String literals use the pinned `standard_conforming_strings=on` policy. The accepted lab used a 12-second budget and independently recorded the actual session settings. JDBC connect timeout is five seconds and socket timeout is the execution budget plus five seconds. The execution budget starts after pinned-distribution verification and bounded observer startup; identity probing and observer/version-command startup have their own bounds. Local manifest I/O is outside the CLI execution budget. Oracle process-budget start and configuration remain unchanged.

Before launching `migrate`, Manager durably associates the job/command with a server-generated application tag. A reproducibly compiled Java 11 helper uses the pinned JDBC jar and a separate verified, read-only connection to record backend PID/start time, transaction/query start, state and wait event. The CLI PID and its verified private process-group ID are fsynced before waiting; the journal directory entry is synced before launch. Metadata journals are private, bounded, and retained outside temporary command workspaces; restart imports valid journal events into the original run's logs without rewriting native command evidence. A complete valid journal prefix can survive abrupt power loss or a write failure; malformed or truncated records are rejected. Missing imported metadata does not establish a successful outcome and the stream stays held.

Startup imports retained valid PostgreSQL journals synchronously before dispatch starts, HTTP serving begins, or any database inspection. Registry query or import persistence errors abort startup and release its process lock; missing or malformed individual journal files leave their streams held. Qualification exposed a slow earlier held run delaying later journal imports; the fix preserves the original five-second assertion. A focused regression fails against the old ordering and passes while the first database inspection is deliberately blocked.

Local cancellation stops the CLI process group. PostgreSQL server-side limits bound surviving execution; the helper observes disappearance. It never calls a database session cancellation or termination function. Manager waits at most six seconds for helper completion, then reaps the helper and records an uncertain outcome if disappearance was not verified. The live acceptance measures backend disappearance independently; helper return is not rollback evidence. Application tags are correlation metadata and cannot establish session ownership: a live regression deliberately copies the tag on another same-role connection and proves that connection is not signalled. Missing/incomplete output or unverifiable disappearance remains uncertain and cannot become success.

Every PostgreSQL migration failure or uncertain result becomes `NEEDS_REVIEW`, with the stream held, migration failure recorded, and Repair skipped. Previously committed scripts remain committed; only the observed failing transaction's rollback is established. A blocked queued successor does not execute. Restart reconciles through inspection and imports evidence but does not replay, retry, release a hold, Repair, Clean, Baseline or edit history. A new idempotency key cannot escape a held stream. Separately justified operator recovery is still required; this increment provides no hold-release or arbitrary SQL endpoint.

Runtime bounds and helper hashes enter the PostgreSQL frozen configuration. Queued work rechecks the profile, credential version, artifact bytes, authorization, history and stream state before dispatch. Unexpected identity, TLS trust, database or PostgreSQL major fails closed. The UI reads the server-owned engine capability. PostgreSQL migration is enabled only for the qualified profile; Oracle retains its policy, and other engines remain unavailable.

## Qualification limits

Qualification is the local Linux Manager with PostgreSQL **17.11**, Flyway **13.10.3**, pgJDBC **42.7.14**, password/SCRAM, verify-full trust, existing lowercase unquoted schemas/roles/databases, and same-schema history. The pinned lab image and loopback-only endpoint are unchanged from foundation acceptance. No other major, managed service, certificate-client authentication, quoted identifier or nontransactional migration profile is accepted.

Migration SQL is trusted administrative code constrained by database privileges. The admission filter rejects known unsupported concurrent/nontransactional, transaction-control, session-control and routine statements at preflight, submission, worker and runtime boundaries. Maintenance admission also conservatively rejects statement-level CLUSTER, ALTER SUBSCRIPTION and partition detach as families: PostgreSQL 17 documents transaction restrictions for [CLUSTER](https://www.postgresql.org/docs/17/sql-cluster.html), [subscription changes](https://www.postgresql.org/docs/17/sql-altersubscription.html), and [concurrent partition detach](https://www.postgresql.org/docs/17/sql-altertable.html). Transactional ALTER TABLE … CLUSTER ON remains admitted. These stricter checks were added during final review and have separate preflight/submission/runtime and live lab evidence. It is not a complete SQL parser or sandbox. Indirect side effects, privileged migration authors changing server/session settings, external effects and arbitrary nontransactional scripts are outside the qualified contract. Schema configuration does not prevent cross-schema access granted by PostgreSQL.

## Final PR review

The final independent source review found a startup ordering gap in the initial PR head `a61144f`: dispatch and journal reconciliation started concurrently, so startup could return before retained PostgreSQL journals were imported. Recovered streams remained held, but independent new work could start before import finished. The final fix makes local journal import a synchronous startup prerequisite, preserving asynchronous database Info/Validate reconciliation. A blocking-reader regression proves startup and queued independent work wait for import; the original head fails this test. Focused post-fix tests and a fresh real PostgreSQL shutdown/restart capture are retained in [final review evidence](evidence/postgresql-migration-20261017/final-review/).

Embedded helper regeneration uses JDK 21 with `--release 11 -proc:none -g:none`; both generated classes match their committed bytes and pinned SHA-256 constants. Review confirmed runtime/database timeout policy, read-only observer identity, private process groups, append-only journals, held failures/no replay, restricted SQL and server capabilities, Oracle/historical behavior, and evidence credential exclusion. No other database engine, deployment setting, runtime pin or database schema migration is changed.
