# Minimal engine-aware reference architecture

Proposal, 2026-10-17; **not implemented**. Preserve the Go modular monolith, SQLite registry, CLI subprocess, encrypted credentials, authorization, immutable artifacts, audit and async run history. No service split, external database, new queue or runtime change is needed.

## Resource semantics

Keep `Project → registered Instance → Schema → Migration stream`, with **Execution Account mapped to allowed Schema IDs**, not owned by a schema or project. “Instance” continues as the operator's registered connection scope: one database/service endpoint, not necessarily an entire physical server. This avoids inserting a new Database parent and reparenting every permission, artifact, project membership and run.

| Engine | Registered Instance / connection profile | Schema scope | Account and history |
| --- | --- | --- | --- |
| Oracle | Host/port + service/PDB, TCP/TCPS; existing IDs | Unquoted Oracle schema, current uppercase behavior | User/schema relationship and current cross-schema mappings; history in selected schema |
| PostgreSQL | Host/port + **database**; register two databases on the same server as two Instances | Existing schema within that database; role is not a schema | Database login role; explicit per-schema allowlist; one history table per stream |
| SQL Server | Host/port + **catalog/database**; named instance resolved to a declared endpoint later | Schema within selected catalog | Server login versus database user/effective permissions must be distinguished; defer until adapter qualification |
| MySQL | Host/port + selected **database** | Database and schema are synonyms; expose one selected scope, not a fictitious nested schema | Account identity includes server-side user/host semantics; history table in database |
| MariaDB | Same resource shape as MySQL, separate engine discriminator and validation | Database/schema synonym | Separate driver/version and permission acceptance; no automatic MySQL equivalence |

Whole-instance project membership includes present/future registered schemas **of that database/service only**. It must not discover or grant other databases on a shared server. No automatic database enumeration is needed for P1: Admin enters a database, tests it, then selects visible schemas. The current authorized history joins remain ID-based and use current membership, not historical project attribution.

## Typed connection profile

The smallest profile has engine, host, port, exactly one engine destination (`oracle_service` or `database_name`), authentication kind, TLS policy/trust reference and profile revision. Existing name/environment/active metadata and account credential references remain. History schema/table belongs to the registered schema, not the shared profile. Credentials remain on execution accounts; do not duplicate passwords into profiles or runs.

| Field | P1 contract |
| --- | --- |
| `engine` | Closed server-side enum `oracle`, `postgresql`; immutable after creation. Future enums admitted only with qualified adapters |
| Destination | Oracle keeps service/transport. PostgreSQL requires explicit database name; no default database from username or URL |
| `auth_kind` | Password only for PostgreSQL; SCRAM negotiation handled by pinned pgJDBC. No pgpass, cloud IAM, Kerberos or interactive login |
| TLS | New PostgreSQL requires `verify-full`, declared host and approved CA bundle reference; no trust-all toggle, custom socket factory or user class name. Optional plaintext only in a later explicit local-lab policy; no downgrade fallback |
| Trust material | Managed non-secret CA bundle, content hash and revision; private staged path generated by server. Do not edit the pinned JRE truststore or include host paths in profile input. Unsupported trust formats fail closed |
| Identifiers | First slice explicitly supports lowercase unquoted PostgreSQL database/schema/role identifiers, including leading underscore, max 63 bytes; history table same subset. Engine-specific rules, no uppercase coercion |
| Advanced options | No raw JDBC URL, TOML, arbitrary properties, init SQL, locations, command args, executable/resolver classes, provisioners or schema creation |

PostgreSQL TLS mapping uses pgJDBC `sslmode=verify-full` and a staged `sslrootcert`; [pgJDBC documents certificate and hostname verification](https://jdbc.postgresql.org/documentation/ssl/). Preserve exact credential bytes via the existing private TOML/literal serialization, not URL embedding. The existing runtime checks/redaction envelope is reused after engine-specific validation. CA content changes invalidate readiness/configuration identity, even if the reference ID is unchanged. Client certificates/keys need a separate encrypted-material lifecycle and are deferred.

## Adapter boundary

Introduce a small engine registry inside the service, selected from persisted profile engine, never from a user-supplied driver class or a JDBC URL guess. Each adapter owns four responsibilities:

1. **Normalize/validate:** engine-specific identifiers, destination, approved TLS/auth settings and supported version policy.
2. **Probe/discover:** fixed read-only queries, actual session user/database/server identity, visible schemas, excluded/system scope handling, privilege observations with potential/unknown/unsupported classification.
3. **Build invocation:** typed URL and semantic configuration; resolve the exact manifest-pinned JDBC module/driver; retain the shared private process envelope and fixed command allowlist.
4. **Interpret/recover:** verify expected database identity and native evidence shape; choose a conservative failure policy and history capability, separate from the shared queue/state machine.

Reuse Oracle's Java/JDBC helper pattern so the connection wizard and Flyway use the **same pinned driver/TLS semantics**. A new Go PostgreSQL driver would introduce a second connection implementation to qualify. Implement a distinct small PostgreSQL helper/query set or a fixed protocol with engine dispatch, never a generic query execution endpoint. Keep helper compilation reproducible and its bytes/digest verified, following the existing Oracle helper pattern. No helper was created in Phase 6.

PostgreSQL probe opens only the declared database, uses bounded connection/read/process budgets and fixed metadata queries, and returns the actual database, session/current role, server version and visible schemas. Assess database CONNECT, schema USAGE/CREATE and ownership/role observations without executing DDL or changing roles/search path. Metadata gaps yield unknown, not inferred global authority. Exclude catalog/system/temp namespaces; allow `public` only when explicitly selected and classified. Save repeats the probe and atomically persists selected references/mappings, preserving the existing wizard contract.

Do not use CLI `testConnection` as discovery: it lacks schema/privilege evidence and unrestricted environment provisioning/init settings can have effects. Do not classify support solely from a successful TCP connection, plugin load, JDBC authentication or one successful SELECT.

## Shared execution path and policy

`REST request → current RBAC + account allowlist → immutable artifact + stream reconstruction → engine adapter → private pinned CLI → append-only command/run evidence → post-operation verification`.

The existing preflight and worker recheck current authorization, activity, mapping and credential revision before dispatch. Reuse idempotency, queue ordering, execution limits, checksum enforcement, locks, no implicit SQL retry, audit and historical snapshots. Info remains a separate bounded inspection, requires operate permission for refresh and creates no migration job/reservation. Recorded viewing still requires read permission only.

For PostgreSQL P1, accept ordinary transactional V/R SQL, same-schema history, no implicit baseline, no schema creation, no out-of-order/cherry-pick/skip flags, no callbacks/placeholders. Retain validation and malformed/unknown evidence handling. Reject or block known unsupported nontransactional operations before enabling that policy, and qualify the runtime's actual behavior rather than promising a complete SQL classifier. `CREATE INDEX CONCURRENTLY` is specifically outside initial support: PostgreSQL's advisory-lock mode and per-script transaction configuration need separate design. Do not rewrite submitted SQL to make it pass.

**Recovery is engine policy.** Keep existing constrained Oracle automatic failed-row repair unchanged. New engines have no automatic Repair. Any failed PostgreSQL Migrate enters a held review path; retain before/after Info+Validate when possible and original failure. Even proven transactional rollback does not make the failed artifact eligible for implicit replay. Cancellation, timeout, output truncation or restart remains ambiguous and held. Do not infer that a whole migration run rolled back: earlier successful scripts can already be committed. A supported reconciliation/retry action requires its own future reviewed design; manually editing SQLite to release a hold is not an accepted workflow.

## Backward-compatible evolution from SQLite v7

Design a subsequent checksummed migration only after approval of implementation scope. **No SQL migration was authored or executed here.** A practical minimal design is:

| Registry change | Compatibility contract |
| --- | --- |
| Extend `database_targets` with `engine` default `oracle`, `database_name` default empty, `profile_revision`; retain `service`, `transport`, IDs and existing columns | Old records retain exact Oracle endpoint semantics. New PostgreSQL targets have empty Oracle-only service; database_name is explicit, never hidden in service |
| Rebuild target uniqueness as partial engine-aware indexes | Existing `(host,port,service)` uniqueness retained for Oracle; PostgreSQL uses `(engine,host,port,database_name)`. Leaving the old global index would wrongly block two PostgreSQL databases with empty service |
| Add profile/TLS settings side table keyed to target ID, and non-secret trust bundle metadata/content or existing safe material store | Explicit auth/TLS version, no secrets in JSON profile; fail closed if an enabled non-Oracle target lacks a profile. No defaults that silently downgrade TLS |
| Reuse `target_schemas`, accounts, credential ciphertext and per-account schema mappings | MVP lowercase PostgreSQL identifiers fit the retained NOCASE uniqueness as a deliberate subset. Before quoted/case-sensitive identifiers or SQL Server collations, replace name uniqueness with adapter-derived identity keys via a separately accepted rebuild |
| Keep grants/projects/artifacts/streams/jobs/run/log/capture foreign keys and IDs | No reparenting, synthetic database rows, automatic grants, project backfill, artifact copying or history rewrite |
| Version new semantic snapshots/fingerprints | Legacy snapshots decode as Oracle **in memory**; leave stored JSON, checksums, credential bytes and historical output unchanged |

The target-table rebuild must use the established dedicated-connection/foreign-key-safe transactional pattern from migration 007, preserve all child references and custom-object safeguards, verify integrity/foreign keys and rollback on error. Inspect actual schema/indexes first; do not simply drop a referenced parent table with enforcement enabled. Upgrade rehearsal must include populated v7 with all tables, run/audit evidence and original external key. Old binaries must reject the new schema; rollback means a coordinated backup restore and compatible binary, never starting the v7 binary against upgraded data.

Legacy Oracle stream fingerprints must remain **byte-for-byte version 1** for unchanged profiles. An in-memory `engine=oracle` default must not be serialized into old fingerprint inputs or mutate historical run JSON. New profiles use fingerprint/snapshot version 2 covering engine, database/service, endpoint/environment, exact schema/history, auth kind, TLS/trust content hash, policy version and runtime pin. Account and credential revisions remain recorded under the existing execution identity rules; credential rotation must not rewrite history or silently rebind a queued plan. Avoid putting cosmetic profile metadata into stream identity. Changes to an active stream's effective destination/configuration must block until reviewed, as today.

## REST and frontend compatibility

Keep existing routes and target/schema/account IDs. Existing Oracle client payloads with no engine retain Oracle semantics on legacy endpoints; new non-Oracle creation requires an explicit engine-aware profile. Never infer PostgreSQL because a service field looks like a database. Existing Oracle connection-response fields remain available; introduce a tagged engine-neutral discovery envelope for new clients, retaining Oracle-specific observations under an engine details object. Unknown engines fail validation.

Expose qualified capability state from a server-owned registry, with separate module/driver/edition/version/policy readiness. The UI presents enabled engines only after their acceptance gates; no raw command picker. Fields are Database for PostgreSQL, Catalog/Database for SQL Server, Database for MySQL/MariaDB and Service/PDB for Oracle. Schema catalog/history/Info must always show engine and database-qualified destination; do not join unrelated objects by display name. Keep canonical schema links and Viewer data minimization.

Verification expectations and promotion order are in the [implementation plan](prioritized-implementation-plan.md). Future SQL Server may reuse the same profile shape but needs its own login/user, catalog/collation and failure adapter; MySQL/MariaDB require database-as-schema semantics and independent driver acceptance. No generic database dropdown can substitute for those contracts.
