# Scoped observability deployment proposal

**Do not apply without explicit approval.** The original Collector configuration was deployed under explicit authorization on 2026-10-18; its two isolated-source events failed outbound DNS and were not delivered. The updated full-header initializer awaits its CI gate before rollout. Existing Manager configuration remains unchanged. Review with [feature contract and acceptance](../../docs/elastic-cloud-integration.md).

`kubectl kustomize deploy/observability` renders one ConfigMap, one Deployment, one ClusterIP Service, two namespaced NetworkPolicies and one CiliumNetworkPolicy in existing namespace `flyway-manager`. Deployment request 50m/64 MiB, limit 200m/256 MiB, one replica; nonroot UID/GID 10001, read-only root, no privilege escalation/capabilities/service-account token, no PVC/hostPath/cluster permissions. Cilium DNS and FQDN rules allow only the exact supplied Elastic endpoint on HTTPS. Kubernetes additive Manager egress allows only the internal collector on 4318. Existing Oracle/PostgreSQL/DNS rules remain in place. Validate live Cilium policy composition and cluster capacity before approval.

The collector exposes only mTLS OTLP HTTP 4318 and has no public ingress. Its private server identity requires SAN `flyway-manager-observability.flyway-manager.svc.cluster.local`, serverAuth EKU, and a dedicated CA. This lab certificate also includes IP SAN `127.0.0.1` for the explicitly authorized loopback port-forward acceptance; that procedure verifies the IP SAN and never disables TLS checks. The separate in-pod probe verifies the exact Service DNS SAN. A Service-only certificate cannot be used with the loopback procedure. Only the approved Manager client identity should be issued clientAuth by that CA. Keep the CA private key in protected operator storage, not cluster/Git/evidence. TLS Secrets are proposed, not verified:

- `flyway-manager-observability-tls`: collector `tls.crt`, `tls.key`, `ca.crt` (client trust).
- `flyway-manager-observability-client-tls`: Manager `tls.crt`, `tls.key`, `ca.crt` (server trust).
- Existing verified reference `flyway-manager-elastic-api-key/OTEL_EXPORTER_OTLP_HEADERS`: full SDK-style header string, consumed only by the nonroot auth initializer. The older `api-key` entry is unused. Metadata checks do not validate its value.

Operator provisions TLS materials in a private 0700 directory with 0600 files, validates chain/SAN/EKUs/expiry and creates Secrets using `kubectl create secret generic NAME --from-file=...` with file **paths**, never key/password values in arguments. Do not print generated manifests. Review rotation before touching an existing Secret; no overwrite commands are supplied here. Secret encryption at rest is not established.

`manager-config-proposal.json` is a disabled configuration fragment to merge into existing config; replacing the entire live config would be unsafe. Enable only after authorized rollout. `manager-trust-proposal.yaml` is a separate strategic merge sketch for the existing `manager` container and Secret mount. Both are **excluded** from the collector kustomization; adapt/render via established GitOps chart and verify the exact diff before authorization. Application deployment/rollback retains original data/PVC/master key and unchanged SQLite schema.

The collector configuration has no credentials: a pinned auth initializer validates the full Secret-sourced OTLP header configuration inside the Pod and writes a mode-0600 header map to a 1 MiB tmpfs. The Collector reads it through its file provider. Only fixed validation markers are logged; values are never displayed or read through the Kubernetes API. No extra `ApiKey` prefix is added. Use no debug exporter or payload/HTTP-header logging. Its receiver authenticates dedicated client certs and drops foreign service/environment/version records; its independent field allowlist removes arbitrary bodies/attributes. It cannot authorize individual user claims and does not mount the registry.

Before any apply, record the rendered object inventory, immutable image/config hash, Secret metadata, Cilium enforcement and resource capacity. Acceptance must include actual indexed search and dashboard evidence. A collector-only readiness result cannot authorize the existing Manager configuration change or establish ingestion acceptance.

Collector internal counters bind only to `127.0.0.1:8888` and can be inspected through an authorized pod port-forward. No Service or NetworkPolicy exposes this diagnostic listener; it has no event payloads. Receiver accepted/exporter sent/failed counters separate internal receipt and transport completion from indexing.
